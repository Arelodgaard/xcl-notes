### C01 Entry point, launcher, config, reporting
`xcl run` is a two-process design in one binary. The launcher resolves the package root, title and exe (from `MicrosoftGame.config` or folder scan), creates `%LOCALAPPDATA%\XCL\<title>\…`, loads and resolves `xcl.toml`, writes `boot.json`, runs GPU/DXC/CPU preflight checks, and re-spawns xcl.exe with `XCL_HOST` and the game's command line. The host initialises logging, HLE, VFS, hooks and the crash handler in a fixed order, then calls the loader. `report.json` gathers imports, called stubs, VFS misses and subsystem stats.
Key: `launcher::run` (`src/launcher.rs:288`), `spawn_host` (`launcher.rs:433`), `host::host_main` (`src/host.rs:11`), `Config`/`Config::resolve`/`Boot` (`src/config.rs:10`, `:80`, `:264`), `manifest::parse` (`src/manifest.rs:40`), `state::config` (`src/state.rs:18`), `preflight::checks` (`src/preflight.rs:57`), `report::write_final` (`src/report.rs:171`), `log::write` + `xlog_*!` (`src/log.rs:72`), `util::dll_key` (`src/util.rs:136`), xcl.exe TLS callback (`src/main.rs:16`), `build.rs` (no high-entropy ASLR; translator source hashes).

### C02 PE loading, import resolution, stubs, TLS, exceptions
XCL's own PE loader maps game images into the host process, applies relocations, and resolves every import eagerly by a fixed policy: HLE route → game DLL → Windows DLL → cross-HLE name → logging stub. It recreates OS loader services: static TLS through a synthesised "TLS carrier" DLL (with slot 0 handed to the title exe), DllMain/TLS-callback thread notifications driven from xcl.exe's TLS callback, `.pdata` registration plus a `RtlPcToFileHeader` detour for C++ exceptions, and crash, abort and stack-cookie diagnostics. A vectored handler emulates AMD-only console CPU instructions (CLZERO, RDPRU, RDPID, MONITORX/MWAITX, EXTRQ/INSERTQ).
